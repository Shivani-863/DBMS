01

ER Models & Relational Design

▶
The Basics

Entities, Attributes & Relationships

An Entity is a real-world object distinguishable from other objects (e.g., Student, Course). An Attribute is a property of an entity (e.g., Name, RollNo). A Relationship is an association among entities (e.g., Student enrolls in Course).

Types of Attributes

  • Simple: Atomic, not divisible (Age, Salary)
  • Composite: Divisible into sub-parts (Name → First + Last)
  • Multi-valued: Can hold multiple values (Phone_Numbers) — drawn with double ellipse
  • Derived: Computed from another attribute (Age ← DOB) — drawn with dashed ellipse
  • Key Attribute: Uniquely identifies entity instances — underlined

Cardinality Ratios

TypeExampleNotation
1:1Person — PassportEach person has at most 1 passport
1:NDept — EmployeeOne dept has many employees
M:NStudent — CourseMany students enroll in many courses

Participation Constraints

  • Total (mandatory): Every entity must participate — double line in ER diagram
  • Partial (optional): Some entities may not participate — single line
Deep Dive

Minimal Table Count Rules (ER → Relational)

The exam-critical skill is counting the minimum number of tables required.

Rule 1: Strong Entity Set

Always becomes exactly 1 table. Primary key = key attribute(s).

Rule 2: Weak Entity Set

Becomes 1 table. Its primary key = partial key + primary key of the owner (identifying) entity. The relationship with its owner does not need a separate table.

Loan(Loan_No, Amount)    -- strong
Payment(Loan_No, Payment_No, Date)   -- weak; Loan_No FK references Loan

Rule 3: Binary Relationships

CardinalityParticipationTables NeededStrategy
M:NAny3 (min)Separate relationship table with both PKs as composite PK
1:NPartial:Any2Add FK on the N-side (many side) referencing 1-side PK
1:NTotal on N-side2Same as above; totality captured via NOT NULL on FK
1:1Both Partial3 or 2Merge relationship into either entity, or keep separate
1:1One Total2Add FK into the entity with total participation (guarantees non-null)
1:1Both Total1 (min)Merge all into single table — guaranteed 1-to-1 mapping
Key Formula: Minimum tables = (# strong entities) + (# weak entities) + (# M:N relationships) + adjustments for multi-valued attributes (each → +1 table) + (# ternary/higher-degree relationships).

Multi-Valued Attributes

Each multi-valued attribute becomes a separate table containing the entity's PK + the attribute value. E.g., Emp_Phone(EmpID, Phone).

Weak Entity — Detailed Rules

  • Identified by a partial key (dashed underline in ER)
  • Depends on an identifying (owner) entity via an identifying relationship (double diamond)
  • Always has total participation in identifying relationship
  • If owner is deleted → cascade delete weak entities (referential action)

Specialization / Generalization

Superclass/subclass hierarchy. Three mapping strategies:

StrategyTablesProCon
Method 1: Single table1Simple queriesMany NULLs; violates domain integrity
Method 2: Table per subclass + super1 + nClean, no nulls for specific attrsJoins needed for complete info
Method 3: Table per subclass only (disjoint, total)nNo joins for subclass queriesSuperclass attrs replicated; overlapping fails

Constraints on Specialization

  • Disjoint (d): Entity belongs to at most one subclass
  • Overlapping (o): Entity may belong to multiple subclasses
  • Total (double line): Every superclass entity must be in some subclass
  • Partial (single line): Some superclass entities may not be in any subclass

Ternary vs. Binary Decomposition

A ternary relationship R(A,B,C) maps to 1 table with {PK_A, PK_B, PK_C} as composite PK (for M:N:N). Cannot always be replaced by binary relationships without information loss. Decompose only if the ternary can be reconstructed via natural join of the binary projections (i.e., satisfies a join dependency).

Exam trap: "Replace ternary with three binaries" — this loses information unless the ternary has specific join dependencies. The safe answer is: ternary relationship needs its own table.
Short Tricks
  • M:N always = 3 tables minimum (2 entities + 1 junction). Non-negotiable.
  • 1:1 both total = merge into 1 table (minimum possible). Look for "both double lines."
  • 1:N → FK goes to N-side. "Many side gets the foreign key."
  • Weak entity never adds an extra table for its identifying relationship — it's already captured in its own table's composite PK.
  • Multi-valued attribute → always +1 table.
  • Derived attribute → 0 extra tables (not stored).
  • Count tables formula on MCQ: T = Estrong + Eweak + RM:N + Amulti-val
  • For 1:1 partial-partial: could be 2 or 3 tables. Question usually asks "minimum" → 2 (merge relation into one entity table).

Q2.

A 1:1 relationship with total participation on both sides can always be mapped to a single relation by merging all entities and the relationship into one table.

When both entities have total participation in a 1:1 relationship, they can be merged into one table with combined attributes. This guarantees exactly one instance per entity pair.

  • 3
  • 4

Q4.

  • LoanNo only
  • (LoanNo, PaymentNo) composite

Weak entity PK = partial key + owner's PK. This composite key uniquely identifies each payment within a loan.
TRUE/FALSE

Q5.

A derived attribute (like Age computed from DOB) requires a separate table in the relational schema.

Answer: FALSE
Derived attributes are computed on-the-fly and need not be stored. They don't require extra tables in the schema.

  • Create a separate relationship table

Each multi-valued attribute gets its own table: {PK, AttrValue}. Two attributes = two separate MVA tables.
TRUE/FALSE

Q8.

In a ternary M:N:N relationship, all three entities contribute their PKs to form the composite PK of the relationship table.

Answer: TRUE
For M:N:N ternary relationships, the junction table's PK is typically the combination of all three entity PKs (or a subset if functional dependencies exist). Most exam questions assume full composite.

02

Relational Model & Algebra

▶
The Basics

Relations and Keys

A Relation is a table with rows (tuples) and columns (attributes). The schema defines structure; the instance is current data.

Key TypeDefinitionExample
Super KeyAny set of attributes that uniquely identifies a tuple{EmpID}, {EmpID, Name}, {EmpID, Name, Salary}
Candidate KeyMinimal super key (no proper subset is also a super key){EmpID}, {Email}
Primary KeyChosen candidate key; cannot be NULLEmpID
Foreign KeyAttribute referencing the PK of another relationDeptID in Employee → Dept.DeptID

Basic RA Operations

  • σ (Select): Filters rows — σcondition(R)
  • π (Project): Filters columns — πattrs(R)
  • ⋈ (Natural Join): Joins on common attributes
  • ∪, ∩, − (Set ops): Require union-compatible relations
  • × (Cartesian Product): All combinations of tuples
  • ρ (Rename): Renames relation/attributes
Deep Dive

Division Operator

R ÷ S returns tuples in R[A] that are associated with every tuple in S. Used for "find all X that have done Y for ALL Z" type queries.

$$R \div S = \pi_{A}(R) - \pi_{A}((\pi_{A}(R) \times S) - R)$$

Where A = R's attributes not in S. This equivalence is the standard derivation from primitive operators.

-- Example: Students enrolled in ALL courses taught by Prof X
-- Enrolled(SID, CID), Courses(CID)
Result = Enrolled ÷ Courses

Outer Joins and NULLs

Join TypeBehaviorNULLs
Left Outer ⟕All tuples from left; unmatched right = NULLRight side attrs
Right Outer ⟖All tuples from right; unmatched left = NULLLeft side attrs
Full Outer ⟗All tuples from both sidesEither side

NULL comparisons: NULL = NULL is UNKNOWN, not TRUE. Use IS NULL / IS NOT NULL.

Three-valued logic: TRUE, FALSE, UNKNOWN. WHERE UNKNOWN → row excluded.

Tuple Relational Calculus (TRC)

Non-procedural query language. A query has the form: {t | P(t)} where P is a formula.

TRC Formulas

  • Atoms: s ∈ R, s.A op c, s.A op t.B
  • Operators: ∧ (AND), ∨ (OR), ¬ (NOT), ∃ (exists), ∀ (for all)

Safe vs. Unsafe Expressions

A TRC expression is safe if it guarantees a finite result. An expression is unsafe if it can produce an infinite result.

Unsafe example: {t | ¬(t ∈ Employee)} — returns all possible tuples NOT in Employee, which is infinite.

Safety condition: all values in the result must come from the domain of the expression (the finite set of constants and values appearing in the relation instances referenced).

Universal Quantifier Equivalence

$$\forall t \in R(P(t)) \equiv \neg \exists t \in R(\neg P(t))$$

This is used to convert ∀ queries into ∃ (which is easier to evaluate).

Integrity Constraints

  • Domain constraint: Attribute values must be from their domain
  • Entity integrity: Primary key cannot be NULL
  • Referential integrity: FK value must exist as PK in referenced relation OR be NULL
  • Semantic integrity: Business rules (e.g., Salary > 0)
Short Tricks
  • Division = "for all" queries. Whenever you see "finds students enrolled in ALL courses," think ÷.
  • Super Key ⊇ Candidate Key ⊇ Primary Key. Every CK is a SK. Not every SK is a CK.
  • NULLs disappear in WHERE conditions — UNKNOWN rows are filtered out.
  • Natural join eliminates duplicate columns; theta join does not.
  • TRC safe rule: All values in result must come from the explicitly referenced relations. Any result pulling values "from outside" known data is unsafe.
  • Left outer join tuple count: ≥ |R| (always at least as many tuples as left relation).
  • Candidate keys: find all minimal sets. On MCQs, verify minimality — remove each attribute; if it still uniquely identifies tuples, it's not minimal.

03

Normalization

▶
The Basics

Anomalies & Normal Forms

When a relation is poorly designed, it suffers from anomalies:

  • Insertion anomaly: Cannot insert data without providing unrelated data
  • Deletion anomaly: Deleting a row removes unintentionally required information
  • Update anomaly: Updating one fact requires changing multiple rows
Normal FormRequirement
1NFAll attributes are atomic (no repeating groups, no multi-valued)
2NF1NF + No partial dependency (non-prime attr must depend on whole PK)
3NF2NF + No transitive dependency (non-prime attr depends only on PK)
BCNFFor every FD X→Y, X must be a super key
4NFBCNF + No non-trivial multi-valued dependencies
5NF4NF + No join dependencies (cannot be reconstructed from projections)

Functional Dependency (FD)

X → Y means: knowing X uniquely determines Y. E.g., RollNo → Name.

  • Trivial FD: Y ⊆ X (e.g., {A,B} → A)
  • Non-trivial FD: Y ⊄ X
Deep Dive

Armstrong's Axioms (Complete & Sound)

  1. Reflexivity: If Y ⊆ X, then X → Y
  2. Augmentation: If X → Y, then XZ → YZ
  3. Transitivity: If X → Y and Y → Z, then X → Z

Derived rules:

  • Union: X→Y, X→Z ⟹ X→YZ
  • Decomposition: X→YZ ⟹ X→Y and X→Z
  • Pseudotransitivity: X→Y, WY→Z ⟹ WX→Z

Attribute Closure Algorithm

To find X+ (closure of attribute set X under FD set F):

closure = X
repeat:
  for each FD (Y → Z) in F:
    if Y ⊆ closure:
      closure = closure ∪ Z
until no change
Use case: X is a super key iff X+ = all attributes. X is a candidate key iff X+ = all attributes AND no proper subset of X has this property.

Minimal Cover (Canonical Cover) Fc

A minimal set of FDs equivalent to F. Steps:

  1. Single RHS: Split all FDs into single-attribute RHS: X→YZ becomes X→Y, X→Z
  2. Remove extraneous LHS attributes: For X→A, check if (X−B)+ already contains A for each B ∈ X. If yes, remove B.
  3. Remove redundant FDs: For each X→A, check if A ∈ (F − {X→A})+ using remaining FDs. If yes, remove X→A.

Lossless Join Decomposition

Decomposition of R into R1, R2 is lossless-join iff:

$$(R_1 \cap R_2) \to R_1 \quad \text{OR} \quad (R_1 \cap R_2) \to R_2$$

i.e., the common attributes form a super key of at least one of the decomposed relations. This is the FD-based lossless condition (for binary decomposition).

General test (Chase algorithm): Create a tableau. Apply FDs. If any row becomes all-distinguished variables (a1, a2, ..., an), decomposition is lossless.

Dependency Preservation

A decomposition preserves dependencies if F+ = (F1 ∪ F2 ∪ ... ∪ Fk)+, where Fi = FDs in F+ that involve only attributes of Ri.

Algorithm to check: For each FD X→Y in F, compute X+ using only FDs within individual decomposed relations (local closure). If Y ⊆ computed closure, FD is preserved.

BCNF vs. 3NF — Critical Distinction

PropertyBCNF3NF
DefinitionFor every X→Y (non-trivial), X is super keyFor every X→Y (non-trivial), X is super key OR Y is prime attribute
Lossless JoinAlways achievableAlways achievable
Dependency PreservingNot always possibleAlways possible
RedundancyMinimalSome allowed
Classic exam scenario: If asked for decomposition that is BOTH lossless AND dependency-preserving, use 3NF (BCNF might not preserve all dependencies). This is a critical distinction.

3NF Synthesis Algorithm

  1. Find minimal cover Fc
  2. Create relation for each FD in Fc: Ri(X ∪ A) for X→A
  3. If no relation contains a candidate key of R, add a relation with a candidate key
  4. Remove any relation whose schema is a subset of another relation's schema

BCNF Decomposition Algorithm

  1. Find a non-trivial FD X→Y that violates BCNF (X not super key)
  2. Decompose R into R1(X ∪ Y) and R2(X ∪ (R − Y))
  3. Repeat for each resulting relation until all are in BCNF

4NF — Multi-Valued Dependencies (MVD)

X →→ Y (X multi-determines Y) means: for each value of X, the set of Y values is independent of the Z values (where Z = R − X − Y).

$$\text{Trivial MVD: } X \twoheadrightarrow Y \text{ if } Y \subseteq X \text{ or } X \cup Y = R$$

4NF: For every non-trivial MVD X →→ Y, X must be a super key.

Every FD X→Y implies MVD X →→ Y (but not vice versa).

5NF — Join Dependencies

A Join Dependency ⋈{R1,...,Rn} holds if R = R1 ⋈ R2 ⋈ ... ⋈ Rn. 5NF (PJNF): every JD is implied by candidate keys. Rarely tested directly; understand conceptually.

Short Tricks
  • Closure test for candidate key: Compute X+; if it equals all attributes, X is a super key. If no proper subset has same property, X is CK.
  • "BCNF can't always preserve dependencies" — this is the single most-tested BCNF fact. If MCQ asks which normal form guarantees both lossless and dependency preserving: 3NF.
  • Lossless test (binary): Common attrs → one of the two sides = lossless. Memorize: R1 ∩ R2 must be a key of R1 or R2.
  • 2NF violation: Non-prime attribute depends on part of composite PK. If PK is single attribute → automatically in 2NF.
  • 3NF violation: A→B→C where A is PK, B is non-prime, C is non-prime. Transitive chain.
  • Prime attribute = attribute that appears in at least one candidate key. Everything else is non-prime.
  • MVD rule: If X→Y (FD), then X →→ Y (MVD). The converse is false.

Q1.

Given R(A,B,C,D) with FD: A→B, C→D. Which key(s) is/are candidate keys?

  • {A, C, D}

  • X ⊆ Y

Trivial MVD: X →→ Y iff Y ⊆ X (always satisfied) or X ∪ Y = R (functional dependency). Non-trivial requires neither condition.
04

SQL Queries

▶
The Basics

SELECT / WHERE / JOIN

SELECT E.Name, D.DeptName
FROM Employee E
JOIN Department D ON E.DeptID = D.DeptID
WHERE E.Salary > 50000
ORDER BY E.Name ASC;

Execution Order (Logical)

FROM → JOIN → WHERE → GROUP BY → HAVING → SELECT → DISTINCT → ORDER BY → LIMIT

This order is crucial: aliases defined in SELECT cannot be used in WHERE (they haven't been evaluated yet).

GROUP BY & HAVING

SELECT DeptID, COUNT(*) AS NumEmp, AVG(Salary)
FROM Employee
GROUP BY DeptID
HAVING COUNT(*) > 5;
Deep Dive

Correlated vs. Non-Correlated Subqueries

TypeCharacteristicPerformance
Non-correlated (nested)Inner query runs once, result used by outerEfficient — inner executes 1 time
CorrelatedInner query references outer query's row; runs once per outer rowExpensive — inner executes N times
-- Non-correlated: inner runs once
SELECT Name FROM Employee
WHERE DeptID IN (SELECT DeptID FROM Department WHERE Location = 'Delhi');

-- Correlated: inner references outer.Salary
SELECT e1.Name FROM Employee e1
WHERE Salary > (SELECT AVG(Salary) FROM Employee e2 WHERE e2.DeptID = e1.DeptID);

HAVING without GROUP BY

When HAVING is used without GROUP BY, the entire table is treated as one group. This allows aggregate conditions on the whole table.

SELECT MAX(Salary) FROM Employee HAVING COUNT(*) > 10;
-- Returns MAX(Salary) only if the table has more than 10 rows; else empty result

Window Functions

Window functions perform calculations across related rows without collapsing them into groups (unlike GROUP BY).

SELECT Name, Salary, DeptID,
  RANK() OVER (PARTITION BY DeptID ORDER BY Salary DESC) AS rnk,
  DENSE_RANK() OVER (PARTITION BY DeptID ORDER BY Salary DESC) AS dense_rnk,
  ROW_NUMBER() OVER (PARTITION BY DeptID ORDER BY Salary DESC) AS rn
FROM Employee;
FunctionBehavior on tiesExample (salaries: 100,100,80)
RANK()Ties get same rank; next rank skips1, 1, 3
DENSE_RANK()Ties get same rank; next rank does NOT skip1, 1, 2
ROW_NUMBER()Always unique; ties broken arbitrarily1, 2, 3

Window Frame Clause

SUM(Salary) OVER (ORDER BY HireDate ROWS BETWEEN UNBOUNDED PRECEDING AND CURRENT ROW)
-- Running total

Set Operations

OperatorDuplicatesSQL Standard
UNIONRemoves duplicatesLike ∪ in set theory
UNION ALLKeeps all duplicatesMultiset union
INTERSECTReturns common rows (distinct)Like ∩
EXCEPT / MINUSRows in first not in second (distinct)Like −

All set operations require union-compatible relations: same number of columns and compatible data types.

EXISTS vs. IN

-- EXISTS: correlated, checks if subquery returns any row
SELECT Name FROM Customer C
WHERE EXISTS (SELECT 1 FROM Order O WHERE O.CID = C.CID);

-- IN: non-correlated, checks membership in result set
SELECT Name FROM Customer
WHERE CID IN (SELECT CID FROM Order);

EXISTS is generally faster for large subquery results (stops at first match). IN materializes the full subquery result.

NULL Handling in SQL

  • NULL = NULL evaluates to UNKNOWN (not TRUE)
  • NULL IN (1,2,NULL) evaluates to UNKNOWN
  • COUNT(*) counts NULLs; COUNT(col) ignores NULLs
  • SUM, AVG, MAX, MIN — all ignore NULLs
  • NOT IN with NULLs: if subquery contains NULL, NOT IN returns UNKNOWN → no rows match!
Exam trap: WHERE col NOT IN (SELECT ... ) — if the subquery can return NULL, the outer query may return 0 rows even when you expect matches. This is a very common MCQ trap.
Short Tricks
  • RANK skips, DENSE_RANK doesn't, ROW_NUMBER always unique. Mnemonics: DENSE = no gaps. RANK = gaps like real competition.
  • HAVING without GROUP BY = condition on whole table as one group.
  • SELECT alias not available in WHERE (WHERE executes before SELECT). Use a subquery/CTE if needed.
  • NOT IN with NULLs → always 0 rows. Use NOT EXISTS instead when nulls possible.
  • UNION removes duplicates (expensive); UNION ALL doesn't. When asked for "all results including duplicates," use UNION ALL.
  • Correlated subquery = runs N times (once per outer row). Non-correlated = runs once.
  • COUNT(*) vs COUNT(col): * includes nulls, column name excludes nulls.

File Organization & Indexing

▶
The Basics

Disk Blocks & Basic Indexing

Data is stored in blocks (pages) on disk. I/O is measured in block transfers, not individual records. Block size is typically 512 bytes to 16 KB.

Types of Indexes

TypeDefinition
Primary IndexIndex on ordered file; search key = ordering field (often PK). Sparse or dense.
Clustering IndexOn non-key field that the file is physically ordered on
Secondary IndexOn any non-ordering field; always dense (or uses bucket pointers)
Dense IndexOne index entry per record
Sparse IndexOne index entry per block (only for sequentially ordered files)
Deep Dive

B-Tree vs. B+ Tree

PropertyB-TreeB+ Tree
Data pointersIn all nodes (internal + leaf)Only in leaf nodes
Leaf linkingNot linkedLinked list (sequential scan efficient)
Key duplicationKeys appear onceKeys may appear in internal nodes AND leaves
Range queriesInefficient (in-order traversal)Efficient (scan linked leaves)
Usage in DBMSRareUniversal (MySQL InnoDB, PostgreSQL)

B+ Tree Order Calculation

Given: Block size = B bytes, key size = V bytes, pointer size = P bytes.

Internal Node Order n (max keys)

Internal node: n search keys + (n+1) pointers must fit in one block:

$$n \cdot V + (n+1) \cdot P \leq B$$ $$n \leq \frac{B - P}{V + P}$$

Leaf Node Order (record pointers)

Leaf: k key-pointer pairs + 1 next-leaf pointer:

$$k \cdot (V + P_{record}) + P_{next} \leq B$$ $$k \leq \frac{B - P_{next}}{V + P_{record}}$$

Tree Height

With N records and leaf order k, internal order n:

$$\text{Height} = \lceil \log_{\lceil n/2 \rceil}(N) \rceil + 1$$

Minimum height ≈ logn(N). Each level access = 1 block read.

B+ Tree Worked Example

Block = 1024 B, Key = 10 B, Pointer = 6 B
Internal order: n(10) + (n+1)(6) ≤ 1024 → 16n ≤ 1018 → n = 63
Leaf: k(10+6) + 6 ≤ 1024 → 16k ≤ 1018 → k = 63

Extendible Hashing

Dynamic hashing that uses a directory (array of 2d pointers) and buckets.

  • Global depth d: Number of bits used from hash to index directory
  • Local depth di: Number of bits that determine bucket membership for bucket i
  • When a bucket overflows: if di = d → double directory (d++). If di < d → split bucket only.
  • Directory size = 2d entries. Multiple directory entries can point to same bucket.
$$\text{Directory size} = 2^d \quad \text{(doubles when global depth increases)}$$

Linear Hashing

Splits buckets in a fixed linear order (not necessarily the overflowing bucket).

  • Split pointer sp tracks next bucket to split (starts at 0)
  • Hash functions: hi(k) = k mod 2iN (where N = initial buckets)
  • If hash value < sp → use hi+1; else use hi
  • No directory needed; overflow buckets used temporarily

Primary vs. Clustering vs. Secondary Index Comparison

FeaturePrimaryClusteringSecondary
File orderingOrdered on key fieldOrdered on non-key fieldUnordered (or different order)
DensitySparse possibleSparse possibleMust be dense
Per relationOneOneMany
I/O for lookupO(log n) blocksO(log n) blocksHigher (random I/O)
Index density rule: Sparse index is only valid when records are physically ordered by the indexed attribute. Secondary indexes are always dense (or use indirection levels).
Short Tricks
  • B+ Tree: data only in leaves. Range queries → scan linked leaf list.
  • Internal node order formula: n = floor((B−P)/(V+P)). Memorize this.
  • Extendible hashing: overflow → double directory if local depth = global depth.
  • Linear hashing: no directory, splits are linear/sequential.
  • Secondary index = always dense (can't be sparse since file isn't ordered by that field).
  • B-Tree ≠ B+ Tree. On MCQs: "data pointers in all nodes" → B-Tree. "data pointers only in leaves" → B+ Tree.
  • Height of B+ tree with N leaves of order n: height ≈ logn/2(N).

Transactions & Concurrency

▶
The Basics

ACID Properties

PropertyMeaning
AtomicityAll or nothing — transaction fully completes or fully aborts
ConsistencyTransaction takes DB from one valid state to another
IsolationConcurrent transactions appear serial to each other
DurabilityCommitted transactions survive failures (persisted to disk)

Transaction States

Active → Partially Committed → Committed (success path)

Active → Failed → Aborted (failure path)

Aborted → Restarted (or Killed)

Deep Dive

Conflict Serializability

Two operations conflict if: they belong to different transactions, access the same data item, AND at least one is a write.

Conflict pairs: (Ri, Wj), (Wi, Rj), (Wi, Wj) on same item.

Precedence Graph (Serialization Graph)

  1. Create node for each transaction Ti
  2. Draw edge Ti → Tj for each conflicting pair where Ti's operation comes before Tj's
  3. Schedule is conflict-serializable iff precedence graph is acyclic
  4. Topological order of acyclic graph = equivalent serial schedule

View Serializability

Schedule S is view-equivalent to serial schedule S' if for every data item Q:

  1. Same initial reads: If Ti reads initial value of Q in S, Ti reads initial value of Q in S'
  2. Same updated reads: If Ti reads value written by Tj in S, same in S'
  3. Same final writes: The transaction that writes final value of Q is same in both
Every conflict-serializable schedule is view-serializable. The converse is false. Schedules with blind writes (writing without reading) may be view-serializable but not conflict-serializable.

Schedule Recoverability Classification

TypeDefinitionCondition
RecoverableIf Tj reads data written by Ti, Ti must commit before Tj commitsNo cascade aborts guaranteed, but cascades can happen
Cascadeless (ACA)Tj can only read data written by committed TiPrevents cascading aborts; stronger than recoverable
StrictTj cannot read or write data written by Ti until Ti commits/abortsSimplest recovery; every strict schedule is cascadeless
$$\text{Strict} \subset \text{Cascadeless (ACA)} \subset \text{Recoverable}$$

Two-Phase Locking (2PL)

Each transaction must obey two phases:

  • Growing phase: May acquire locks; cannot release any
  • Shrinking phase: May release locks; cannot acquire any new locks

Lock point: Moment transaction acquires its last lock.

2PL guarantees conflict-serializability. Topological order = order of lock points.

Variants of 2PL

VariantRuleGuarantees
Basic 2PLStandard growing/shrinkingConflict-serializable; deadlocks possible; not strict
Strict 2PLExclusive locks held until commit/abortConflict-serializable + strict (recoverable)
Rigorous 2PLAll locks held until commit/abortConflict-serializable + strict; order = commit order
Conservative 2PLAcquire all locks before transaction beginsDeadlock-free; but impractical (predeclare all data)

Multiple Granularity Locking

Lock granularity hierarchy: DB → Area → File → Page → Record (tuple)

Intention locks are required at ancestor nodes before locking at finer granularity:

Lock ModeMeaning
IS (Intention Shared)Will lock some descendant with S
IX (Intention Exclusive)Will lock some descendant with X
S (Shared)Read the node and all descendants
X (Exclusive)Write the node and all descendants
SIX (Shared + Intention Exclusive)Read all, write some descendants

Compatibility Matrix

Timestamp Ordering (TO)

Each transaction Ti is assigned timestamp TS(Ti) at start. Read/Write rules:

Read(Q) by Ti:

  • If TS(Ti) < W-timestamp(Q): Ti is reading an item overwritten by a newer transaction → rollback Ti
  • Else: Execute read; update R-timestamp(Q) = max(R-timestamp(Q), TS(Ti))

Write(Q) by Ti:

  • If TS(Ti) < R-timestamp(Q): An older Ti trying to write a value that was already read by a newer transaction → rollback Ti
  • If TS(Ti) < W-timestamp(Q): Ti trying to write obsolete data → Thomas Write Rule: skip (ignore) this write
  • Else: Execute write; update W-timestamp(Q) = TS(Ti)
Thomas Write Rule: If TS(Ti) < W-timestamp(Q), the write by Ti is obsolete — a newer transaction has already written Q. Simply ignore the write (don't rollback). This allows more schedules to proceed but means the schedule may not be conflict-serializable (though it is view-serializable).
Short Tricks
  • Conflict test: same item, different transactions, at least one write.
  • Precedence graph cycle → not conflict-serializable. Acyclic → take topological sort for equivalent serial schedule.
  • Strict ⊂ ACA ⊂ Recoverable. Memorize the hierarchy. More restrictive = earlier in chain.
  • 2PL → conflict-serializable (always). Strict 2PL → also strict/recoverable.
  • Thomas Write Rule = skip the write, don't abort. It relaxes conflict-serializability but maintains view-serializability.
  • Blind write: Writing Q without reading Q first. Can create view-serializable but conflict-non-serializable schedules.
  • IX + S = not compatible. SIX = S + IX for a node where you read all but write some.
  • Deadlock detection: wait-for graph (simpler than precedence graph — edges only for lock waits). Cycle = deadlock.

Backup & Recovery

▶
The Basics

Failure Types & Log Files

Failure TypeDescriptionRecovery Method
Transaction failureLogical error or deadlock abortRollback (undo) the transaction
System (crash) failurePower failure; volatile memory lostRedo committed, undo uncommitted
Disk failureHead crash; disk block corruptionRestore from backup + replay log

Log Records

  • <Ti, start> — transaction started
  • <Ti, X, old_val, new_val> — update record
  • <Ti, commit> — committed
  • <Ti, abort> — aborted
Deep Dive

Write-Ahead Logging (WAL) Protocol

Two critical rules that ensure recoverability:

  1. Undo rule: Before a data item is written to disk, the log record for the update must be written to stable storage (log written before data page)
  2. Redo rule: Before a transaction commits, all its log records (including commit record) must be written to stable storage
WAL Guarantee: If crash occurs, log on stable storage allows recovery. Without WAL, a crash between data write and log write leaves the DB in an unrecoverable inconsistent state.

Checkpointing

A checkpoint writes all modified buffer pages to disk and records which transactions are active, reducing recovery time.

Simple Checkpoint

  1. Stop accepting new transactions temporarily
  2. Wait for all active transactions to finish
  3. Flush all log records and modified buffer pages to disk
  4. Write <checkpoint> record to log
  5. Resume transactions

Recovery: scan back to last checkpoint. Redo transactions that committed after checkpoint; undo those that hadn't committed.

Fuzzy Checkpoints (used in ARIES)

Checkpoint is taken without stopping transactions:

  1. Write <checkpoint begin, L> where L = active transaction list
  2. Flush all modified pages to disk (can happen while transactions continue)
  3. Write <checkpoint end> when flush complete

Advantage: No halt in transaction processing. Recovery uses the last complete fuzzy checkpoint.

ARIES (Algorithm for Recovery and Isolation Exploiting Semantics)

Industry-standard recovery algorithm used in DB2, SQL Server, and many others. Uses LSN (Log Sequence Number) — monotonically increasing number for each log record.

Key Data Structures

  • Log: Sequential file of log records, each with LSN
  • Transaction Table: Active transactions and their last LSN
  • Dirty Page Table (DPT): Pages modified in buffer but not yet written to disk; includes RecLSN (earliest log record that dirtied the page)

Three Phases of ARIES Recovery

Phase 1: Analysis
  • Scan log forward from last checkpoint
  • Reconstruct Transaction Table (find all transactions active at crash)
  • Reconstruct Dirty Page Table (find all pages that need redo)
  • Determine RedoLSN = min(RecLSN) across DPT entries
Phase 2: Redo
  • Scan log forward from RedoLSN
  • For each update log record: if page is in DPT AND page LSN < current log LSN → redo the operation
  • Repeat all actions (whether transaction committed or not) to restore DB to crash state
  • This phase repeats history exactly
Phase 3: Undo
  • Roll back all transactions that were active at crash time (those not in Transaction Table with commit/abort)
  • Process in reverse LSN order (largest LSN first)
  • For each undo action, write a Compensation Log Record (CLR) — CLR is redo-only (prevents re-undoing if another crash occurs during undo)
  • CLR has a nextUndoLSN pointing to the previous log record to undo
ARIES Key Properties:
(1) Repeating history during redo (even for aborted transactions).
(2) CLRs make undo idempotent (safe to crash during undo and restart).
(3) Steal + No-Force: Buffer manager can write dirty pages before commit (steal), and doesn't force all pages to disk at commit (no-force) → needs undo and redo respectively.

Buffer Policies and Their Impact

PolicyMeaningRecovery Implication
StealDirty pages can be flushed before commitUNDO needed (writes may outlive transaction)
No-StealDirty pages never flushed before commitNo UNDO needed; but poor buffer usage
ForceAll dirty pages flushed at commitNo REDO needed; but expensive I/O at commit
No-ForcePages not forced to disk at commitREDO needed (commits may not be on disk)

ARIES uses Steal + No-Force → requires both UNDO and REDO. Most practical choice.

Short Tricks
  • WAL: log before data. "Write-Ahead" = log record written to stable storage BEFORE data page is written.
  • ARIES: Analysis → Redo → Undo. A-R-U. "ARU" — Analysts Redo the Undo.
  • Redo = repeat history. Undo = roll back losers.
  • CLR = Compensation Log Record. Written during undo. Has nextUndoLSN. Prevents double-undo if crash during recovery.
  • Steal → need undo. No-Force → need redo. ARIES = Steal + No-Force = needs both.
  • Fuzzy checkpoint = no transaction halt. Simple checkpoint = transactions halted. Fuzzy = production-grade.
  • RedoLSN = min(RecLSN in DPT). Redo starts from this point.

  • Fuzzy is concurrent; simple halts transactions
  • Both are identical
  • Depends on buffer size
Answer: B
Fuzzy checkpoint: no transaction halt, I/O proceeds. Simple checkpoint: transactions paused. Fuzzy used in production systems (minimal disruption).
MULTIPLE CHOICE

Q7.

RedoLSN in recovery is set to:

  • The LSN of the last checkpoint
  • Minimum RecLSN of all dirtypage entries
  • The LSN of the oldest transaction
  • The current LSN at crash
Answer: B
RedoLSN = min(RecLSN) from Dirty Page Table. This is the earliest update that might not be persisted, so Redo starts from here.
TRUE/FALSE

Q8.

A committed transaction's changes are always immediately durable (on disk) without Redo.

Answer: FALSE
With No-Force policy, committed changes may be in buffer (not yet on disk). ARIES Redo phase ensures durability even if buffered commits weren't flushed.
SCENARIO BASED

Q9.

Full backup takes the entire database snapshot. Incremental backup takes:

  • Only changed blocks since last full
  • Only changed blocks since last any backup
  • Entire DB every time
  • A sample of random blocks
Answer: B
Incremental: changes since last backup (full or incremental). Differential: changes since last full backup. Incremental uses less space/time.
MULTIPLE CHOICE

Q10.

Point-in-time recovery (PITR) requires:

  • Only a full backup
  • Full backup + all subsequent transaction logs
  • Incremental backups only
  • Real-time replication
Answer: B
PITR: restore from full backup, then replay transaction log up to desired timestamp. Ensures data consistency at any historical point.

Deep Dive

CAP Theorem

In a distributed system, you can guarantee at most 2 of 3 properties simultaneously:

  • C — Consistency: Every read receives the most recent write (or an error). All nodes see same data at same time.
  • A — Availability: Every request receives a (non-error) response, without guarantee it's the most recent data.
  • P — Partition Tolerance: System continues operating despite network partitions (messages lost/delayed between nodes).
Critical insight: Network partitions are inevitable in real distributed systems. Therefore, the practical choice is always between CP and AP (P is non-negotiable).
System TypeExamplesTrade-off
CP (Consistent + Partition-tolerant)HBase, MongoDB (w/ majority write), ZookeeperMay reject requests during partition → sacrifices availability
AP (Available + Partition-tolerant)Cassandra, CouchDB, DynamoDBMay return stale data during partition → sacrifices consistency
CA (Consistent + Available)Traditional RDBMS on single nodeCannot handle network partitions (not truly distributed)

BASE Properties (NoSQL consistency model)

  • Basically Available: System guarantees availability (per CAP)
  • Soft State: State may change over time without input (due to eventual consistency)
  • Eventually Consistent: Data will eventually be consistent across nodes given no new updates

BASE is the antithesis of ACID. Suitable for systems where availability > strong consistency (e.g., shopping carts, social media feeds).

NoSQL Paradigm Matching

TypeData ModelUse CaseExamples

Key-Value Details

Simplest NoSQL model. Operations: GET(key), PUT(key, value), DELETE(key). No query language — must know the key. Values are opaque; no secondary index natively.

Column Store Details

Data is stored column-by-column (not row-by-row). Excellent for analytical queries that access few columns across many rows (OLAP). Poor for row-level transactional updates (OLTP). Cassandra is actually a wide-column store (stores families of columns per row key).

Graph Database Details

Native graph storage with index-free adjacency (each node directly references adjacent nodes). Traversals are O(degree) per hop — extremely efficient for multi-hop relationship queries. RDBMS would require expensive self-joins.

Two-Phase Commit (2PC) — Distributed Transactions

Ensures atomicity across distributed nodes. Two participants: Coordinator (initiates) and Participants (sub-systems).

Phase 1: Prepare (Voting)

  1. Coordinator sends PREPARE message to all participants
  2. Each participant votes COMMIT (if ready) or ABORT (if not)
  3. Participants that vote COMMIT must log the vote and lock resources until phase 2

Phase 2: Commit/Abort (Decision)

  1. If all vote COMMIT → Coordinator sends COMMIT to all
  2. If any vote ABORT → Coordinator sends ABORT to all
  3. Participants execute decision and release locks; send ACK
2PC Failure Scenarios:
— If coordinator crashes after participants vote COMMIT but before sending decision: participants are blocked (hold locks indefinitely) — this is the "blocking problem" of 2PC.
— 3PC (Three-Phase Commit) was designed to address this but is rarely used in practice due to complexity.

2PC vs. Saga Pattern

Aspect2PCSaga

Vector Databases — Fundamentals

Vector databases store and query embeddings — high-dimensional numerical representations of unstructured data (text, images, audio) produced by ML models.

Embeddings

A vector embedding maps an object to a point in high-dimensional space (e.g., 768-dim or 1536-dim) such that semantically similar objects are geometrically close. Generated by models like BERT, OpenAI Ada, etc.

Distance Metrics

MetricFormulaBest For
Euclidean (L2)$\sqrt{\sum(a_i - b_i)^2}$Spatial/geometric similarity; same-scale embeddings
Cosine Similarity$\frac{a \cdot b}{||a|| \cdot ||b||}$Text/semantic similarity (magnitude-invariant)
Dot Product$\sum a_i \cdot b_i$Recommendation systems; normalized embeddings
Manhattan (L1)$\sum |a_i - b_i|$Sparse data; robust to outlier dimensions

Approximate Nearest Neighbor (ANN) Search

Exact nearest-neighbor search in high dimensions is computationally expensive (curse of dimensionality). ANN algorithms trade exact accuracy for speed:

  • HNSW (Hierarchical Navigable Small World): Graph-based; fast, high recall; used in Qdrant, Weaviate
  • IVF (Inverted File Index): Cluster-based; partition space into Voronoi cells; search within nearest cluster
  • PQ (Product Quantization): Compress vectors; trade memory for slight accuracy loss
  • LSH (Locality-Sensitive Hashing): Hash similar vectors to same bucket; fast but lower recall

Popular Vector Databases

  • Pinecone: Managed cloud; simple API; no self-hosting
  • Weaviate: Open-source; hybrid search (vector + keyword); GraphQL API
  • Qdrant: Open-source; Rust-based; HNSW; payload filtering
  • pgvector: PostgreSQL extension; combines relational + vector; no separate DB needed
  • Chroma: Lightweight; embedded; Python-native; common in LLM dev

RDBMS Architecture — 3-Schema Architecture (ANSI/SPARC)

  • External Schema (View level): User-specific views; hides complexity
  • Conceptual Schema (Logical level): Logical structure of entire DB; tables, constraints
  • Internal Schema (Physical level): Physical storage; indexes, file organization

Data Independence:

  • Logical data independence: Changing conceptual schema without changing external schema
  • Physical data independence: Changing internal schema without changing conceptual schema
Short Tricks
  • CAP: pick 2. But P is always needed → real choice is CP vs AP.
  • ACID vs BASE: ACID = RDBMS, strong consistency. BASE = NoSQL, eventual consistency.
  • NoSQL match: Cache/session → Key-Value. Catalog/profiles → Document. Time-series/logs → Column. Social/recommendations → Graph.
  • 2PC blocks on coordinator failure — this is the key weakness. 3PC adds a pre-commit phase to resolve this.
  • Cosine similarity = semantic similarity for text (ignores magnitude; only cares about angle/direction).
  • HNSW = best ANN for most use cases (high recall, fast). LSH = fastest but lowest recall.
  • Logical independence is harder to achieve than physical independence (changing logical structure = changing user views).
  • CA systems (no partition tolerance) = only possible if running on single node. "Distributed CA" is theoretically impossible.

  • Cannot handle network delays
  • Blocks on coordinator failure during prepare phase
  • Requires synchronous communication

Cosine similarity measures the angle between two vectors, ignoring magnitude.

Answer: TRUE
Cosine similarity = (A · B) / (||A|| ||B||). Ranges [0,1]. Useful for text/semantic similarity (e.g., word embeddings) where magnitude is irrelevant.

Q10.
